# Known divergences from pdfminer.six

Everything the port does differently from pdfminer.six, why, and which inputs it affects. Each
entry has an id that the code marks with `// DIVERGE(<id>)`. Nothing that is not listed here may
differ; a difference found by `tools/difftest.py` that is not in this list is a bug.

| id | What differs | Why | Affected inputs |
|---|---|---|---|
| `bigint` | Ints beyond i64 are exact (`Value::BigInt`): tokens, object ids, arithmetic, comparisons, `int()`/`float()` (with Python's `OverflowError`), dict keys and reprs behave as in Python. Where the port needs a machine integer it does not follow Python's big int: `int(x)` for an i64 use (a length, an index, a font cache key) raises `OverflowError` ("int too large for the port (i64)") where Python goes on; a CCITT `/Columns` below i64 keeps only its sign; a generation number beyond i64 saturates; `nunpack` of more than 8 bytes keeps the low 63 bits; ToUnicode CMap codes and CFF INDEX offsets are exact up to 15 bytes (i128), and a ToUnicode entry whose cid is beyond i64 is not stored (Python stores it under a key no cid can look up, visible only in `dump()`). | Machine integers keep the hot paths fast; these uses only see such values in malformed files. | Malformed files with integers of 19+ digits in those places. |
| `int-truediv` | `a / b` of two ints both beyond 2**53 rounds twice. | Same as `bigint`. | Same as `bigint`. |
| `charset-normalizer` | `make_compat_str(bytes)` decodes UTF-8 or falls back to `str(bytes)`; Python guesses the encoding with charset_normalizer. | charset_normalizer is a heuristic with no stable specification. | `HTMLConverter`/`TagExtractor` output for font names or tag properties that are bytes and not UTF-8. |
| `ccitt-alloc` | `CCITTFaxDecoder` with a huge `/Columns`: Python builds `[1] * width` (8 bytes per pixel) and raises `MemoryError` when that allocation fails; the port allocates `width` bytes and raises `MemoryError` above `isize::MAX / 8` or when its own allocation fails, so the width at which `MemoryError` starts differs. | The threshold depends on the machine's allocator in both. | CCITTFax streams with `/Columns` in the billions. |
| `width-range-alloc` | A font `/W` or `/W2` range of more than 2**24 cids raises `MemoryError` at once. pdfminer.six fills its width dict for any range until memory runs out (about 100 bytes per cid), so it raises `MemoryError` (or is killed) somewhere beyond, depending on the machine. | The threshold depends on the machine's memory in Python; the port picks one instead of allocating gigabytes. | Fonts with width ranges of millions of cids (malformed files). |
| `plane-cells` | Layout analysis raises `MemoryError` at once when one object covers more than 2**23 cells of the 50-unit grid (`Plane.add`), or a lookup covers more than 2**32 (`Plane.find`/`remove`). pdfminer.six goes through the cells one by one: `add` fills memory (`MemoryError`, or the process is killed), `find` runs for hours. | Python's outcome depends on the machine's memory and patience; the port picks a bound. | Coordinates in the millions or beyond (malformed files: page boxes or text matrices with huge numbers). |
| `recursion-depth` | Recursion that the input controls (`/Prev` chains, nested object streams, indirect `/Length` cycles, outline siblings, page and number trees) raises `RecursionError` after a fixed nesting budget (990 frames; Python frames between nested `getobj` calls are counted). Layout analysis: `analyze` raises `RecursionError` when Python would exceed its 1000-frame recursion limit, counting frames as if `LTPage.analyze` ran at frame depth 7 (`layout::ANALYZE_FRAME_DEPTH`, the depth under `extract_pages` and `pdf2txt.py`). `get_text()` of a deep group tree does not raise. | Python's limit applies to its whole stack, so the exact depth depends on the caller. | Malicious or cyclic files: the exception class is the same; only how far a finite but extremely deep chain gets differs. |
| `fp-repr` | Exception and log messages that Python formats with `repr(fp)` or `repr(parser)` (`PDFTextExtractionNotAllowed` from `get_pages`, `PDFNoValidXRef` messages of `PDFXRef.load`) say `<file>` / `<PDFParser>`. | The port has no Python object reprs for files. | Message text only; classes are the same. |
| `nonint-objid` | A stream fetched through a non-int object id keeps `objid = None` (Python stores the id object). | `PDFStream.objid` is an `i64`. | Unreachable in practice: non-int ids only come from broken object stream headers, and those entries never lead to a parsed stream. |
| `saslprep-unicode` | `saslprep` (AES-256 R6 passwords) uses the normalization data of the `unicode-normalization` crate, whose Unicode version can differ from Python's. | Python's `ucd_3_2_0.normalize` uses the current decomposition/composition data, as the port does, but of Python's Unicode version. | Passwords with characters assigned after the older of the two versions: always a `PDFValueError`, possibly with the other of its two messages. |
| `cmap-path` | `CMapDB` only knows the cmaps of the pinned `pdfminer/cmap` directory, embedded at build time. Python first looks in `$CMAP_PATH` (default `/usr/share/pdfminer/`), and an absolute cmap name can reach the installed package's directory through its real path. | The port has no installed package directory, and reading cmaps from the file system would make the output depend on the machine. | Machines with files in `$CMAP_PATH` or `/usr/share/pdfminer/`; PDFs naming a cmap by an absolute path. |
| `cmap-case` | Cmap file names are matched case-sensitively (as on Linux). On a case-insensitive file system (macOS by default) Python also loads `h.json.gz` for the cmap name `h`. | Python's own result depends on the file system; the port follows the case-sensitive one. | PDFs whose Encoding/CMap name differs from a pdfminer cmap only in case, run on macOS/Windows. |
| `heap-id-ties` | `LTLayoutContainer.group_textboxes` orders pairs of boxes with equal distances by `id(obj1)`, `id(obj2)`. The port uses the objects' creation order as `id` (`LTItem::id`, a serial number). | CPython's `id` is a memory address, so pdfminer.six's own grouping of tied pairs depends on the allocator: it changes between runs of the same file (seen on `kampo.pdf` and `issue-598-cmap-other-fonts.pdf`). Addresses follow creation order most of the time. `tools/gen_testdata/layout.py` makes Python use the same rule (it replaces `id` in `pdfminer.layout`); a Python reference that keeps the real `id` (e.g. `tools/oracle.py`) is not reproducible on these files. | Pages where two pairs of text boxes or groups are exactly as far apart: `LTPage.groups` and the order (and `index`) of the text boxes can differ from a given pdfminer.six run. Among the samples: `nonfree/f1040nr.pdf`, `nonfree/kampo.pdf`, `contrib/issue-598-cmap-other-fonts.pdf`, `tests/corpus/many-boxes.pdf`. |
| `inline-image-id` | Inline images are named `inline<n>` (the n-th inline image drawn in the run, from 1). Python names them `str(id(obj))`, a memory address that changes between runs. | Python's name is not reproducible, so no port can match it. `tools/pyref.py` makes the reference use the same names. | The `name` of the `LTFigure`/`LTImage` of inline images, in every output that shows it (XML `<figure name>`, exported image file names). |
| `charset-normalizer` (cont.) | `make_compat_str` of bytes with a UTF-16 BOM decodes them as UTF-16 and strips a UTF-8 BOM, as charset_normalizer does; other non-UTF-8 bytes keep the fallback above. | See above. | `tools/difftest.py` lists the one corpus case that still differs (`contrib/issue-598-cmap-other-fonts.pdf`, `-t tag`). |
| `matrix-sequence` | When a `/Matrix` (form XObject or `cm` operands) multiplies into a product entry that is a sequence rather than a number (e.g. string `a` and `b` entries times int CTM entries), the port raises `TypeError` at once. Python keeps the sequence and fails later, in a way that depends on where it is used. | Matrices are `f64` arrays in the port. | Malformed files only. |
| `pillow` | The port behaves like pdfminer.six without Pillow installed: images that need Pillow (`_save_bytes`, CMYK JPEG, JPEG 2000) create an empty file and raise `ImportError`. | No image codec dependency. | `--output-dir` / `ImageWriter` on such images. |
| `codecs` | Only the UTF-8, Latin-1, ASCII, UTF-16 and UTF-32 codecs (with their Python aliases) are known; other codecs (`cp1252`, `shift_jis`, ...) raise `LookupError`. | No codec tables in the port. | `-c`/`codec` options naming other encodings. |
| `stdout-locale` | Text written to stdout is always UTF-8 (with `surrogateescape` in the cases Python uses it); Python uses the locale's encoding. | The port does not read locale encodings. | The CLI under a non-UTF-8 locale. |
| `argparse-terminal` | The CLI help width comes from `$COLUMNS`, else 80; Python also asks the terminal. Python 3.14 colors help and errors on a terminal; the port does not. | Terminal-dependent output. | Interactive `--help` and usage errors only; pipes and files are identical. |
